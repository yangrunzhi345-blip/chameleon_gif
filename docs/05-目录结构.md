## 5.2 目录职责速查

| 目录 | 用途 | 依赖规则 |
|------|------|----------|
| `lib/app` | 组合根:路由、主题、跨模块会话控制器、页面壳 | 可依赖 features(仅组装,不写业务逻辑) |
| `lib/core` | 日志/工具 | **禁止**依赖 domain 与 features |
| `lib/domain` | 实体/值对象/异常/端口接口 | **零依赖**(纯 Dart) |
| `lib/features/*` | 功能模块(converter/import/preview/task_queue/export/history/timeline) | **禁止**互相依赖 |
| `lib/shared` | 平台适配/共享 provider/仓储 | **禁止**依赖 features |
| `lib/features/*/application` | **功能层**(用例/控制器) | 纯 Dart,**禁止 import Flutter UI 库**;仅依赖同模块 domain 与注入接口 |
| `lib/features/*/infrastructure` | 端口实现(允许 Flutter/第三方依赖) | 实现 domain 端口,禁止被 application 反向依赖细节 |
| `lib/features/*/presentation` | **UI 层**(页面/组件) | **禁止业务逻辑**、禁止 import 仓储/基础设施;仅依赖同模块 application |
| `test/` | 单元/Widget 测试 | 镜像 lib 结构 |
| `integration_test/` | 端到端 | 依赖完整应用 |

## 5.3 禁止依赖矩阵(红线)

| 从 \ 到 | domain | core | shared | features/其他 | app |
|---------|--------|------|--------|---------------|-----|
| domain | — | ❌ | ❌ | ❌ | ❌ |
| core | ❌(不得 import domain) | — | ✅ | ❌ | ❌ |
| shared | ✅ | ✅ | — | ❌ | ✅ |
| features/本模块 | ✅ | ✅ | ✅ | ❌(见注) | ❌ |
| features/*/application | ✅ | ✅ | ✅(仅接口) | ⚠️(见注) | ❌ |
| features/*/presentation | ✅(只读) | ✅ | ❌(禁止直调仓储/基础设施) | ❌ | ❌ |
| app | ✅ | ✅ | ✅ | ✅(仅组装) | — |

> **跨模块协作口径(B-3 批准)**:features 各模块 **application 层 controller 间直接 `ref.read`**
> 为已批准协作模式(如 export → task_queue/timeline、timeline → preview/export,
> 见 timeline_controller.dart 与 export_controller.dart 的类注释);**UI 层(presentation)
> 禁止跨模块 import**,跨模块 UI 组合收敛于 `app/presentation` 壳;
> 共享跨功能组件(如 `param_dropdown_field`)驻留所属模块 presentation,由 app 壳复用。
> 已知偏差:shared/platform 下执行器(process_engine/ffprobe_executor 等)的测试
> 暂驻 `test/features/converter/`(见 14-测试计划 §14.2 注),后续随模块归位迁移。

## 5.4 为什么这样组织

| 备选 | 不选原因 |
|------|----------|
| 单层平铺(全部丢 lib/) | 无法支撑队列/历史/批量阶段的复杂度 |
| 按类型分层(models/repos/views 全平铺) | 功能内聚差,改一个功能要跨 5 个目录 |
| 全量 feature-first 无共享层 | shared 的复用会让模块间隐式耦合;显式 shared 目录让复用可见可审 |

**决策依据**:按"功能内聚 + 技术分层"混合组织(即 feature-first + 内部再分 application/presentation + 显式共享层),是 Flutter 社区在中等规模桌面应用上验证过的平衡方案。
