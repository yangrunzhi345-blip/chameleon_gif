# 17 P7+P8 合并执行方案(性能优化 + 测试补齐)

> 前置:P0–P6 已完成(MVP 达成,见 [12-开发计划](12-开发计划.md))。本文为 P7 性能优化与 P8 测试补齐的**合并执行方案**,与 [12-开发计划](12-开发计划.md)、[14-测试计划](14-测试计划.md)、[02-需求分析](02-需求分析.md) §2.5 指标同步维护。

## 一、合并决策

两阶段合并为一阶段执行,理由:

1. **P7 实际工作量已小于计划**:进度流/position 的 200ms 节流已全部落地(3 处,见 §2);剩余主要是启动优化、isolate 化、缩略图缓存与基线采集。
2. **P8 是 P7 的安全网**:P7 改造代码(启动、isolate、缓存)必须有测试防回归,合并后"边改边补测试"反馈更短。
3. **共享测量设施**:P8 的 integration_test 夹具视频正是 P7 基线采集(启动/帧率/内存)的执行载体,一次搭好两处受益。
4. **无功能依赖**:两阶段 WP 均为收尾型,不含新功能;并行窗口规则(12.3 同序号 WP 可同时进行)允许合并。
5. **流程成本减半**:一次计划、一次阶段门、一次完成标注,减少上下文切换(单开发者 + AI 场景下尤其重要)。

**不变项**:提交粒度不变(perf / test 分开提交);P8-WP3 三平台手工清单必须放在最终代码上执行(不得在未优化代码上签字)。

### 合并 WP1:启动优化 + 覆盖率补齐(先补测试再改代码)

**P7 部分 — 启动 ≤2s(冷启动,桌面 SSD)**

1. **路由懒加载 → 评估结论:无需改动**(已核实:go_router 17.3.0 源码 `lib/src/route.dart` 的 `GoRoute` 仅 `builder`/`pageBuilder` 两构造参数,`lazy` 参数已在该大版本移除;页面构建恒为按需——`buildPage` 仅在路由首次导航时调用,路由表定义本身无首帧成本;`deferred import` 对桌面 AOT 无代码加载粒度收益)。`/preview` 的 `state.extra` 传递与构建时机无关,5 个流程测试(独立 GoRouter 实例 + pump)行为不变。原方案此项不再有代码可改,改为在 docs 记录结论。验证:路由可达性测试不破(router 表快照/页面 pump 测试)。
2. **Isar 打开异步化评估**:`main.dart` 中 `Isar.open` 为最大阻塞点。
   - 方案 A(推荐先做):`runApp` 前仅同步轻量初始化(Logger、Prefs),ProviderScope 先挂临时状态,Isar open 在首帧后异步完成,`isarProvider` 用 `AsyncNotifier` 承载;需要 DB 的页面首帧可渲染空态。
   - 方案 B(保守):保持现状,仅记录启动耗时基线,若已 ≤2s 则不动。
   - **决策规则**:先测基线(见合并 WP3 的采集脚本),若冷启动已 ≤2s 且主要耗时不在 Isar,执行方案 B 并在 docs 记录;否则方案 A。
   - ✅ **已执行(2026-08-04)→ 方案 B**:profile 模式 3 次首帧 310/297/296ms(中位 297ms,`flutter run --trace-startup`);env 门控分段(`GIFFORGE_STARTUP_PROFILE=1`)实测 docsDir 29ms / Isar.open 39ms / MediaKit 14ms / prefs 7ms,Isar 占比约 13%——远低于阈值,不改启动结构。`lib/core/utils/startup_tracer.dart` 常驻(默认零开销),供后续对比。基线数值汇总见「六、性能基线」(提交 6)。
3. 顺带:确认 `MediaKit.ensureInitialized()` / `AppLogger` 无同步重活(实测后再定是否延迟)。

**P8 部分 — 覆盖率补齐(按 §2.5 缺口,补在 P7 改动前的代码上)**

| 优先级 | 测试 | 要点 |
|--------|------|------|
| 高 | value_objects 三件套 | task_progress 序列化/percent 钳制;task_state 状态机语义(isPending/isFinal);app_theme_mode 映射 |
| 高 | ThumbnailExtractor 单测 | fake FFmpegEngine 端口注入:抽帧调用、缓存命中不重复抽帧、64 条 FIFO 淘汰、抽帧失败降级返回 null |
| 中 | theme_controller 单测 | 三态切换、持久化读写、非法值回退 |
| 中 | Android 引擎单测 | ffmpeg_kit_engine / ffprobe_kit_executor:命令装配与结果解析(不真调原生库,抽接口/注入 fake 回调);若结构不支持注入,记录为手工清单项并在 docs 标注 |
| 低 | 平台端口 | 维持 fake 替代策略,不补(薄端口,收益低) |

### 合并 WP2:isolate 化 + 缩略图缓存 + integration_test 闭环

**P7 部分**

1. **命令构造/进度解析 isolate 化评估**:
   - 命令构造(每次转换 1 次,重活低)→ **不做 isolate**(收益低,序列化成本反而高),在 docs 记录判断。
   - 进度解析/日志解析(onLog 每帧高频)→ 先实测 onLog 频率与单行 parse 耗时:若 parse 成本显著(单行 > 0.1ms 或高频阻塞 UI),用 `compute` 或流式 isolate 承接;否则维持主 isolate 并记录。**以实测为准,不盲目改造**。
   - ✅ **评估结论(2026-08-04)→ 均不做,记录依据**:命令构造每次转换 1 次且 µs 级,isolate 序列化成本反而更高;进度解析经 `-progress pipe:1` 已 200ms 节流(3 处节流见 §2.1),onLog 仅收 stderr 行且 `TaskManager` 根本不传 onLog(LogParser 无正则,µs 级),"onLog 每帧高频"前提不成立。判断记录于此,不再改造。
2. **缩略图磁盘缓存**:`thumbnail_extractor.dart` 在内存 Map 前加磁盘层(已有 `$cacheDir/thumb_<hash>.png` 落盘,补:启动/会话间复用磁盘命中、磁盘 LRU 清理策略、读盘失败降级)。UI 端评估 `Image.memory` → `FileImage` + `ImageCache`(由 Flutter 管理缓存与内存上限)。
   - ✅ **已实现(2026-08-04)**:磁盘层落地——稳定 key(base64Url + 长度前缀,不引入 crypto 依赖)、跨实例磁盘命中(源 mtime 新于 png 时重抽,源缺失仍命中)、按 mtime LRU 惰性清理(首用扫 ≤256,写盘后 >384 防御清理)、读盘异常删 png 回落重抽。内存 64 FIFO/putIfAbsent 语义不变。
   - **UI 端 FileImage 评估 → 不做**:缩略图 ≤64 条 × ~1MB 峰值远低于 ImageCache 默认上限;autoDispose family 滚动回收 + 内存缓存已覆盖滚动重建。改 FileImage 需改 provider 返回形态 + 磁盘 LRU 删除时 UI errorBuilder,风险/收益不划算。判断记录于此。
3. **日志写节流**:onLog 逐行分级写日志,确认 `AppLogger` 无同步 IO 热点(若写盘同步,批量/异步化)。
   - ✅ **评估结论(2026-08-04)→ 不节流,记录依据**:`AppLogger` 仅 console 输出(logger 包,无文件落盘,文件落盘属后续阶段),"写盘同步"问题不存在;onLog 路径低频(见上 isolate 评估)。判断记录于此。

**P8 部分 — integration_test 全链路 + 性能基准**

1. **全链路集成测试**(`integration_test/`,`-d linux`):批量导入(多选)→ 双槽并发 → 单任务取消 → 历史自动入库 → 崩溃恢复(进程重启等价:重开仓储断言重排)。夹具用现有 clip_a/clip_b/clip_long,不足则 `tool/gen_fixtures.sh` 补一段 ≥10s 视频(性能测试用)。
2. **性能基准脚本**:`tool/perf_benchmark.dart`(或集成到 integration_test):
   - 启动时间:进程起 → 主页首帧(实测值 vs ≤2s)
   - 转码中 UI 帧率:长视频转码期间采集帧间隔(≥55fps)
   - 内存峰值:500MB 视频导入+预览+转码全程(≤1.5GB;本地无 500MB 样本则用 clip_long 放大倍率折算,记录折算方法)
   - 输出:结构化记录(时间/环境/数值)追加到 docs/17 或独立基线文件
3. **覆盖率基线对比**:复跑 `flutter test --coverage`,与合并 WP1 基线对比,确认 P7 改动未引入覆盖回退。

**验收**:集成测试全链路通过;覆盖率三项达标(converter ≥85%、task_queue ≥80%、domain ≥90%,lcov 汇总);性能基准记录在案。
