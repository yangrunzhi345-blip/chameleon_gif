## 5.2 目录职责速查

| 目录 | 用途 | 依赖规则 |
|------|------|----------|
| `lib/app` | 应用根、路由、主题、注入 | 可依赖 features 的根级组装(仅 app.dart) |
| `lib/core` | 常量/异常/日志/工具 | **禁止**依赖 domain 与 features |
| `lib/domain` | 实体/值对象/接口 | **零依赖**(纯 Dart) |
| `lib/features/*` | 8 个功能模块 | **禁止**互相依赖 |
| `lib/shared` | 跨功能基础设施 | **禁止**依赖 features |
| `lib/features/*/application` | **功能层**(用例/控制器) | 纯 Dart,**禁止 import Flutter UI 库**;仅依赖同模块 domain 与注入接口 |
| `lib/features/*/presentation` | **UI 层**(页面/组件) | **禁止业务逻辑**、禁止 import 仓储/基础设施;仅依赖同模块 application |
| `test/` | 单元/Widget 测试 | 镜像 lib 结构 |
| `integration_test/` | 端到端 | 依赖完整应用 |

## 5.3 禁止依赖矩阵(红线)

| 从 \ 到 | domain | core | shared | features/其他 | app |
|---------|--------|------|--------|---------------|-----|
| domain | — | ❌ | ❌ | ❌ | ❌ |
| core | ❌(不得 import domain) | — | ✅ | ❌ | ❌ |
| shared | ✅ | ✅ | — | ❌ | ✅ |
| features/本模块 | ✅ | ✅ | ✅ | ❌(禁止跨模块) | ❌ |
| features/*/application | ✅ | ✅ | ✅(仅接口) | ❌ | ❌ |
| features/*/presentation | ✅(只读) | ✅ | ❌(禁止直调仓储/基础设施) | ❌ | ❌ |
| app | ✅ | ✅ | ✅ | ✅(仅组装) | — |

> 跨模块协作一律通过 **Application 用例 Provider**(同模块外的类型以接口形式注入),见 [04-系统架构](04-系统架构.md) §4.3。

## 5.4 为什么这样组织

| 备选 | 不选原因 |
|------|----------|
| 单层平铺(全部丢 lib/) | 无法支撑队列/历史/批量阶段的复杂度 |
| 按类型分层(models/repos/views 全平铺) | 功能内聚差,改一个功能要跨 5 个目录 |
| 全量 feature-first 无共享层 | shared 的复用会让模块间隐式耦合;显式 shared 目录让复用可见可审 |

**决策依据**:按"功能内聚 + 技术分层"混合组织(即 feature-first + 内部再分 application/presentation + 显式共享层),是 Flutter 社区在中等规模桌面应用上验证过的平衡方案。
